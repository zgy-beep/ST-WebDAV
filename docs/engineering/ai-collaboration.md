# AI 协同开发指南

> 与 `../AGENTS.md` 配合使用；本文件更具体，冲突时以本文件为准。
> 目标：让「人 + AI」成为一个高效且可控的团队，而不是让 AI 变成一个**不用负责的**打字机。

---

## 1. 为什么需要这份指南

AI 写代码的速度是人手的十倍，但**犯错的成本也在放大十倍**：
一次静默的范围扩大、一次没验证就宣称「已修复」、一次没经确认的推送，都可能污染主干。

这份指南解决三件事：

1. **谁做什么** —— 分工边界清晰，避免人做 AI 的活（浪费），也避免 AI 做人的活（失控）。
2. **怎么协作** —— 任务怎么拆、怎么交接、怎么验收。
3. **怎么把关** —— 代码审查与验收标准，明确「什么算完成」。

---

## 2. 分工边界

### 2.1 人负责什么（不可委托）

| 职责 | 为什么必须是人 |
|---|---|
| **产品决策** | 要什么、不要什么、优先级 —— 这是价值判断，不是实现问题 |
| **需求拆解与验收标准定义** | 验收标准定义错了，AI 会高效地做错事 |
| **架构与技术选型** | 决定了未来所有工作的天花板 |
| **破坏性变更决策** | 删除、改名、不兼容 —— 需要对用户负责 |
| **外部动作授权** | 推送、建 PR、提 issue、发布 —— 这些是**代表用户**的行为 |
| **最终验收与放行** | 合并前的那个人签字 |
| **风险取舍** | 已知缺陷是修还是接受，是业务判断 |

### 2.2 AI 负责什么

| 职责 | 说明 |
|---|---|
| **代码实现** | 按既定设计写代码，包括样板、胶水、边界处理 |
| **代码阅读与定位** | 在陌生代码库里找出根因、梳理调用链 |
| **测试编写** | 复现用例、边界用例、回归断言 |
| **重构执行** | 在人给定边界内做机械迁移 |
| **文档撰写** | README、CHANGELOG、注释、ADR 草稿 |
| **一致性检查** | 找出散落各处的版本号、命名不一致、重复代码 |
| **初轮自审** | 按清单自查自己的产出 |
| **问题结构化** | 把模糊的问题问成可回答的问题 |

### 2.3 共同完成

| 事项 | 人 | AI |
|---|---|---|
| 需求澄清 | 判断真实意图 | 提出澄清问题、列出歧义点 |
| 方案设计 | 拍板选型 | 给出 2~3 个方案 + 各自取舍 |
| 调试 | 判断「合不合理」 | 复现、缩小范围、收集证据 |
| 性能优化 | 定义「够快」 | 测量、对比、给数据 |
| 审查 | 最终判断 | 首轮自查、风险提示 |

### 2.4 红线

- ❌ AI **不得**自行执行外部动作（push / PR / issue / 发布 / 发消息）——必须先获得明确指示。
- ❌ AI **不得**自行决定删除数据、删除目录、清理工作区。
- ❌ AI **不得**在未运行测试的情况下宣称「已修复」。
- ❌ AI **不得**自行扩大改动范围。
- ❌ AI **不得**代替人做产品与技术决策。

## 3. 任务拆解

### 3.1 拆解原则

| 原则 | 说明 | 反例 |
|---|---|---|
| **一个任务 = 一次可交付** | 做完能独立验证、独立提交 | 「重构整个前端」 |
| **有明确验收标准** | 说清「做完是什么样」 | 「优化一下性能」 |
| **有明确边界** | 说清「不许碰什么」 | 不说 → AI 会顺手改 |
| **能独立验证** | 有办法确认做对了 | 只有人眼能判断 |
| **先拆后写** | 超过 3 个文件先出计划 | 直接开干 |

### 3.2 拆解层级

```
 Epic（一个可交付的产品能力）
  └─ Story（一组用户故事，通常 1~3 天）
       └─ Task（一次具体改动，半天内可完成）
            └─ Sub-task（可选，1 小时内）
```

**Task 的粒度标准**：AI 能在一个会话内完成并自测；人能在 5 分钟内看完 diff。

### 3.3 给 AI 的任务描述模板

**用这个模板给 AI 派活**，信息越全，返工越少：

```markdown
## 目标
<一句话说清要达成什么结果>

## 背景
<为什么需要这个改动。相关 issue、上下文、已确认的结论>

## 范围
### 要做
- ...
### 不做（重要）
- ...

## 约束
- 必须遵循的既有约定（引用具体文件/规则）
- 不能修改的文件/目录
- 性能、兼容性、安全方面的硬性要求

## 参考实现
<仓库里类似的、已经做好的东西，指出具体文件路径>

## 验收标准
- [ ] 可验证的条件 1
- [ ] 可验证的条件 2

## 交付要求
- 跑 `npm test` 并贴真实输出
- 按 ../AGENTS.md §9 的格式汇报
```

**示例（真实场景）：**

```markdown
## 目标
世界书条目列表支持多选后批量追加标签。

## 背景
issue #58。用户在条目多的书里逐条加标签太慢，需要批量操作。
现有条目列表已有 hover 态多选框的交互基础。

## 范围
### 要做
- 列表顶部加批量操作工具条（选中数量 + 追加标签 + 移除标签）
- 标签冲突时弹确认（复用 ui-kit Panel）
- 批量结果写入变更记录

### 不做
- 不做跨书批量
- 不改世界书编辑器以外的任何模块
- 不动 `src/client/vendor/ui-kit/`

## 约束
- 新样式必须用 `.st-webdav-` 前缀，只用 `var(--nvui-*)` 令牌
- 标签写入必须走现有 ai-prompts.js 的解析路径，不新写解析
- 变更记录格式与现有单条操作保持一致

## 参考实现
- `src/client/index.js` 的面板渲染流程（保持一致）
- `style.css` 的面板样式

## 验收标准
- [ ] 选中 3 条记录后可一次追加标签，刷新后仍在
- [ ] 标签冲突时弹确认，取消则不写入
- [ ] 批量操作产生一条变更记录，可撤销
- [ ] `npm test` 全绿

## 交付要求
- 贴真实测试输出
- 附 UI 变更截图
```

### 3.4 渐进式披露

不要一次把整个仓库塞给 AI。按需给：

```
第 1 轮：让 AI 先读并概述现状（不写代码）
第 2 轮：让 AI 定位根因并给方案（不写代码）
第 3 轮：确认方案后实现一个最小切片
第 4 轮：跑测试 → 自审 → 汇报 → 人工评审
```

> **先读后写**是本项目最重要的一条协同原则。

## 4. 执行流程

```
人：定义目标 + 验收标准 + 边界
        ↓
AI ：读代码 → 定位 → 出计划（含改动文件清单与影响面）
        ↓
人 ：确认计划（或调整）
        ↓
AI ：实现 → 加测试 → 跑全量 → 自审
        ↓
AI ：按 §7 格式汇报（改了什么 / 为什么 / 验证 / 下一步）
        ↓
人 ：审查 diff + 验证结果 → 通过则提交/合并
```

**中途介入点**：AI 的计划阶段是**最便宜**的纠错时机。此时改一个方案，成本是几分钟；写完再改，成本是几小时。

## 5. 代码审查

### 5.1 三道关

| 关卡 | 执行者 | 检查什么 | 阻断性 |
|---|---|---|---|
| **第一关：AI 自审** | AI 自己 | 按 §5.2 清单逐项过 | 是 |
| **第二关：CI** | 自动化 | 测试 + 静态检查 + 规范校验 | 是（红灯不合并） |
| **第三关：人工评审** | 人 | 设计意图、风险、边界 | 是 |

### 5.2 AI 自审清单

**每次改完，AI 必须自己过一遍这张清单再汇报：**

```markdown
### 范围
- [ ] 只改了任务范围内的文件？（列出所有改动的文件）
- [ ] 有没有"顺手"改的东西？（有就说明理由）

### 正确性
- [ ] 边界条件处理了？（空值、空数组、极值、超长输入）
- [ ] 异常路径处理了？（失败时有明确行为，不是静默吞掉）
- [ ] 有没有引入循环依赖？
- [ ] 公共接口变更时，所有调用方都更新了吗？

### 规范
- [ ] 命名符合规范？
- [ ] 有没有调试代码残留？
- [ ] 有没有硬编码的魔法值/密钥/URL？
- [ ] 注释解释的是"为什么"吗？

### 测试
- [ ] 改动有对应测试吗？
- [ ] 测试真的能复现原问题吗？（能先红后绿）
- [ ] 断言的是行为还是实现细节？

### 安全
- [ ] 有没有把用户输入直接拼进 HTML / SQL / 路径？
- [ ] 有没有动到其它模块的数据或设置？

### 上游
- [ ] 有没有修改 `src/client/vendor/ui-kit/` 下的文件？（有 = 违规）
- [ ] 发现的 ui-kit 问题提 issue 了吗？
```

### 5.3 人评审时该看什么

**不要逐行挑格式** —— 格式交给 lint。聚焦这 5 点：

| # | 检查 | 提问 |
|---|---|---|
| 1 | **意图对齐** | 这次改动要解决的问题，真的解决了吗？ |
| 2 | **范围** | 有没有静默扩大范围？有没有影响别的模块？ |
| 3 | **正确性** | 边界、异常、空值、并发处理得住吗？ |
| 4 | **安全** | 有没有越权操作用户数据？注入风险？ |
| 5 | **测试有效性** | 测试如果失败，是因为代码坏了吗？会不会是「假绿」？ |

**评审意见分级**（见 `git-workflow.md` §4.4）：

```
blocking:   必须改，否则不合并
suggestion: 建议改，需回复说明是否采纳
nit:        吹毛求疵，不阻塞
```

### 5.4 高风险改动的额外要求

以下改动**必须由人主导**，AI 只做辅助：

| 改动 | 额外要求 |
|---|---|
| 触碰用户已有数据 / 设置 | 必须先备份 + 写迁移 + 验证旧数据可读 |
| 删除或重命名公开接口 | 必须提供迁移指引 + CHANGELOG 标注 BREAKING CHANGE |
| 升级 ui-kit 大版本 | 必须逐条对照上游破坏性变更清单 |
| 涉及性能改动 | 必须有**改动前后的实测数据对比** |
| 引入新依赖 | 必须说明理由、体积影响、许可证 |

## 6. AI 常见失败模式与对策

| 失败模式 | 表现 | 对策 |
|---|---|---|
| **假装做了** | 声称「已修复」但没跑测试 | 要求贴真实输出；无输出 = 未验证 |
| **范围蔓延** | 顺手重构了 5 个文件 | 任务描述里写死「不做」清单；评审时核对文件列表 |
| **猜路径** | 引用不存在的文件/函数 | 硬规则：先读后写，路径必须来自实际读取 |
| **过度自信** | 「这应该没问题」 | 硬规则：只说验证过的；不确定就标「待验证」 |
| **用直觉代替测量** | 「这里性能有问题」 | 性能结论必须有实测数据（帧间隔/耗时） |
| **静默降级** | 把某个需求悄悄简化了 | 汇报必须列「未完成项」 |
| **反复小修** | 同一问题改了 5 遍还不对 | 停下来重新定位根因，而不是继续打补丁 |

## 7. 验收标准（Definition of Done）

### 7.1 单个任务的完成定义

一个任务只有**全部**满足以下条件才算完成：

```markdown
- [ ] 功能达到预期，验收标准逐条可验证
- [ ] 有对应测试，且测试能复现问题 / 覆盖新逻辑
- [ ] `npm test` 全绿（贴真实输出）
- [ ] `node scripts/validate-commit-msg.mjs` 通过
- [ ] 自审清单已过
- [ ] 改动范围符合预期，无静默扩大
- [ ] 未修改上游组件库（`src/client/vendor/ui-kit/`）
- [ ] 文档已同步（README / CHANGELOG / 注释，按需）
- [ ] 汇报格式完整：改了什么 / 为什么 / 验证结果 / 下一步
- [ ] 未执行任何未授权的外部动作
```

### 7.2 缺陷修复的完成定义

```markdown
- [ ] 有复现步骤的记录（修复前的失败状态可复现）
- [ ] 有回归测试（修复前红、修复后绿）
- [ ] 修复的是根因，不是表象
- [ ] 说明了根因与证据（文件:行号 / 实测数据）
- [ ] 相关的相邻路径也检查过（同类问题是否还有其它触发点）
```

### 7.3 版本发布的完成定义

见 `versioning.md` §8 发布流程。

### 7.4 AI 汇报必须包含

```markdown
## 改了什么
- `文件:行号` —— 改了什么

## 为什么这么改
- 根因：<一句话>（证据）
- 方案取舍：<为什么选 A>

## 验证结果
- `<测试命令>` —— <真实输出>（通过 / N passed）
- `<检查命令>` —— 通过
- ⚠️ 未覆盖：<什么没验证到，为什么>

## 接下来做什么
1. <下一步，带动作主体>
```

## 8. AI 会话使用建议

| 建议 | 理由 |
|---|---|
| **一个会话做一件事** | 上下文干净，不串味 |
| **长任务分轮推进** | 读 → 计划 → 实现 → 验证，每轮确认一次 |
| **让 AI 先复述需求** | 复述偏差是最便宜的纠错点 |
| **主动要证据** | 「给文件路径和行号」「贴真实输出」 |
| **及时纠偏** | 发现方向偏了立刻打断，别等写完 |
| **关键决策留文档** | ADR（`docs/decisions/`），防止重复讨论 |
| **别让 AI 连续跑太久** | 长时间自主执行容易累积未验证的假设 |

## 9. 协同检查表（每个 PR）

**人（合并前）：**

```markdown
- [ ] 我能一句话说清这个 PR 要解决什么
- [ ] 改动文件清单符合预期，没有意外文件
- [ ] AI 的汇报里"验证结果"是真实输出
- [ ] 测试能复现原问题（我认可这个测试的判定力）
- [ ] 没有静默的范围扩大
- [ ] 没有修改上游组件库
- [ ] 破坏性变更已确认并标注重要程度
```

**AI（汇报前自审）：**

见 §5.2 的完整清单。
