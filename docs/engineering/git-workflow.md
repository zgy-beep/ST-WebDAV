# Git 提交与推送规范

> 适用范围：所有分支、所有提交、所有 PR。
> 与 `../AGENTS.md` 配合使用；本文件更具体，冲突时以本文件为准。
> 占位符见 `../AGENTS.md` §0。

---

## 1. 分支模型

### 1.1 分支角色

| 分支 | 用途 | 可否直接推送 | 保护 |
|---|---|---|---|
| `main` | 完整仓库，默认分支，承载开发与评审 | ❌ 禁止（只能走 PR） | 必须保护 |
| `feature/*` | 新功能开发 | ✅ | — |
| `fix/*` | 缺陷修复 | ✅ | — |
| `chore/*` | 构建、依赖、工具链 | ✅ | — |
| `docs/*` | 纯文档变更 | ✅ | — |
| `release/*` | 版本发布准备（仅在需要时） | ✅ | — |
| `hotfix/*` | 线上紧急修复 | ✅ | — |

> 本项目**无发布分支**，产物直接由 `main` 的 Git 标签分发。

### 1.2 分支命名规则

**格式：**

```
<类型>/<简述>
<类型>/<issue 编号>-<简述>
```

**类型取值（仅这 8 个）：**

| 类型 | 用于 | 示例 |
|---|---|---|
| `feature` | 新增功能 | `feature/entry-batch-edit` |
| `fix` | 缺陷修复 | `fix/parser-crash-on-empty` |
| `chore` | 构建/依赖/工具/配置 | `chore/bump-ui-kit-2-5-0` |
| `docs` | 文档 | `docs/add-issue-template` |
| `refactor` | 不改行为的重构 | `refactor/split-runtime-module` |
| `perf` | 性能优化 | `perf/lazy-load-preview` |
| `test` | 测试相关 | `test/add-parser-edge-cases` |
| `release` | 版本发布 | `release/1.2.0` |

**硬性要求：**

1. 简述用 **kebab-case**（小写 + 连字符），全小写，**不得含空格、中文、大写字母**。
2. 简述长度 **3~40 字符**，动词或名词短语，一眼能看出改动内容。
3. 有 issue 关联时，**必须**用 `类型/编号-简述` 形式，便于自动关联。
4. 分支名**不随提交改写**，一个分支只干一件事，中途不要混入无关改动。
5. 临时分支用 `tmp/<描述>`，合并后立即删除。
6. 从 `main` 切出，用完合并后**立即删除分支**。

```bash
# 正例
git checkout -b feature/42-ai-diff-preview
git checkout -b fix/panel-scroll-jump

# 反例（禁止）
git checkout -b Feature/NewFeature
git checkout -b feature/新功能
git checkout -b wip
```

## 2. 提交信息规范（Conventional Commits）

### 2.1 格式

```
<类型>(<范围>): <主题>

<正文>

<脚注>
```

- **首行**：`<类型>(<范围>): <主题>`
  - 主题用**中文**，动词开头，**不加句号**。
  - 首行总长 **≤ 72 字符**（含类型、范围、括号、冒号）。
  - 范围（scope）可省略：`fix: ...`。
- **正文**：空一行后开始，解释**为什么改**（不是复述改了什么）。
  - 每行 ≤ 100 字符。
  - 用空行分段。
- **脚注**：空一行后，可选。
  - `Closes #<编号>` / `Refs #<编号>` —— 关联 issue。
  - `BREAKING CHANGE: <说明>` —— 破坏性变更（必须同时递增主版本号）。
  - `Co-authored-by: <姓名> <邮箱>`。

### 2.2 类型取值

| 类型 | 用于 | 版本影响 |
|---|---|---|
| `feat` | 新增功能 | 次版本号 +1 |
| `fix` | 缺陷修复 | 修订号 +1 |
| `docs` | 文档 | 无 |
| `style` | 纯格式（不改逻辑） | 无 |
| `refactor` | 重构（不改外部行为） | 无 |
| `perf` | 性能优化 | 修订号 +1 |
| `test` | 测试 | 无 |
| `build` | 构建系统、打包 | 无 |
| `ci` | CI 配置 | 无 |
| `chore` | 杂项（依赖、脚本、配置） | 无 |
| `revert` | 回滚 | 视被回滚的提交而定 |

### 2.3 范围（scope）约定

用**模块名**或**目录名**，保持稳定，不要随手造词：

```
feat(editor): 支持批量导入世界书条目
fix(runtime): 修复设置重载后 context 失效
docs(engineering): 补充 ui-kit issue 上报规范
chore(ui-kit): 升级内置 ui-kit 至 v2.5.0
test(parser): 补齐空输入边界用例
chore(release): 发布 v1.2.0
```

### 2.4 示例

**简单修复：**

```
fix(parser): 修复空输入导致的数组越界

parseEntries 在 entries 为空时未提前返回，直接访问 [0] 触发异常。
补充空数组守卫，并在测试中加入空输入断言。

Closes #42
```

**新功能：**

```
feat(editor): 支持条目批量标签

用户在条目列表勾选多条记录后可一键批量追加或移除标签，
标签变更会写入变更记录，支持撤销。

- 新增批量操作工具条
- 新增标签写入前的冲突确认
- 批量操作结果写入 changelog

Closes #58
```

**破坏性变更：**

```
feat(api)!: 运行时设置接口改为异步

initializeRuntime 现在返回 Promise，调用方需 await。
原因：设置迁移需要异步读取宿主存储。

BREAKING CHANGE: initializeRuntime 由同步改为异步，
所有调用方必须等待 Promise 完成后再读取配置。

Closes #61
```

### 2.5 提交粒度

- **一个提交 = 一个完整变更**。能独立回滚的改动独立提交。
- 不要把「修 bug」+「顺手重构」+「更新依赖」混在一起。
- **不要提交半成品**：WIP 用 `git stash` 或本地分支，不要 push 半成品到主干分支。
- 提交前 `git diff --staged` 自查一遍，确认没有调试代码、密钥、临时文件。

### 2.6 提交粒度

```bash
git add -p              # 逐块暂存，把大改动拆成多个提交
git diff --staged       # 暂存区自查
git commit -m "fix(parser): 修复空输入导致的数组越界" -m "补充空数组守卫与回归断言。"
```

## 3. 推送规范

### 3.1 推送前检查清单

- [ ] `npm test` 全绿
- [ ] `node scripts/validate-commit-msg.mjs` 通过
- [ ] `git diff --staged` 已自查，无调试残留、无密钥
- [ ] 提交信息符合 Conventional Commits
- [ ] 提交只做一件事
- [ ] 分支名符合规范
- [ ] 涉及 UI 变更：已附截图或录屏
- [ ] 涉及上游 ui-kit：已按 `docs/ui-kit/issue-reporting.md` 提交 issue，并在代码/提交信息中引用编号

### 3.2 推送动作

```bash
git push -u origin <分支名>
```

**推送是外部动作** —— 除非用户明确指示，否则**只提交不推送**。

### 3.3 代理配置（本机环境）

Git 代理只配给 `github.com`，其他一律直连：

```bash
git config --global http.https://github.com.proxy http://127.0.0.1:10808
```

注意：
- 上面这条**只影响 git 走 github.com 的请求**，`curl` 不受影响，需要时显式 `-x http://127.0.0.1:10808`。
- 环境里注入的 `http_proxy` 不影响 git 配置，但会影响其它命令行工具。

## 4. PR（Pull Request）规范

### 4.1 提交 PR 的前置条件

- [ ] 从 `feature/*` / `fix/*` 等工作分支发起，**不直接推主干**。
- [ ] 分支已同步 `main` 最新状态（rebase 或 merge）。
- [ ] 关联了 issue（PR 描述中写 `Closes #编号`）。
- [ ] 全部检查通过。
- [ ] 自查清单已过（见 §4.3）。

### 4.2 PR 标题格式

```
<类型>(<范围>): <主题>
```

与提交信息首行**保持一致**。示例：

```
feat(editor): 支持条目批量标签
fix(runtime): 修复设置重载后 context 失效
```

### 4.3 PR 描述模板

按下列结构填写（仓库已提供 `.github/PULL_REQUEST_TEMPLATE.md`，创建 PR 时自动带出，本节与其同步维护）。必填项：

```markdown
## 变更内容
<!-- 这次 PR 做了什么，一到三句话。 -->

## 变更原因
<!-- 为什么要改：解决了什么问题 / 实现了什么需求。链接 issue。 -->

Closes #

## 改动范围
- [ ] 仅新增
- [ ] 包含修复
- [ ] 包含重构（说明为何必须重构）
- [ ] 包含依赖升级

## 验证方式
<!-- 实际执行的验证步骤与结果，不是"应该没问题"。 -->
- [ ] 单元测试通过
- [ ] 实机 / 浏览器验证通过
- [ ] 截图 / 录屏（UI 变更必填）

## 风险与回滚
<!-- 可能的副作用、如何回滚。 -->

## 检查清单
- [ ] 测试已添加并通过
- [ ] 文档 / CHANGELOG 已更新
- [ ] 未引入新依赖（或已说明理由）
- [ ] 未修改 `src/client/vendor/ui-kit/` 下的文件
```

### 4.4 评审流程

```
作者提交 PR
    ↓
① 自查（作者）        ← 提交前必须完成 §4.3 清单
    ↓
② AI 初审（可自动）    ← 见 ../engineering/ai-collaboration.md §5
    ↓
③ CI 检查             ← 测试 + 静态检查必须全绿，红灯不得合并
    ↓
④ 人工评审（≥1 人）   ← 重点看设计意图与风险，不逐行挑格式
    ↓
⑤ 合并（squash）      ← 合并后删除工作分支
```

**规则：**

- **红灯不合并**：CI 未通过一律不得合并，除非是已知的、与本次改动无关的既有失败（需在 PR 中注明）。
- **至少 1 人 approve** 才能合并；核心模块（宿主交互、设置存储、UI 组件）需 **2 人**。
- **作者不能 approve 自己的 PR**。
- 评审意见分三级：
  - `blocking:` —— 必须改，否则不合并。
  - `suggestion:` —— 建议改，作者可决定，需回复说明理由。
  - `nit:` —— 吹毛求疵，不阻塞，作者自行判断。
- 作者对每条 `blocking` 意见要么改，要么回复说明为什么不改。**沉默不视为同意**。
- **合并方式**：统一 **squash merge**，PR 标题作为最终提交信息首行，PR 正文作为提交正文。
- **合并后**：立即删除工作分支；更新 `CHANGELOG.md`。

### 4.5 评审者该看什么

按优先级，**不逐行挑格式**（格式交给工具）：

1. **意图**：这次改动要解决的问题是否被真正解决了？
2. **边界**：有没有静默扩大改动范围？有没有影响其它模块？
3. **正确性**：边界条件、异常路径、空值、并发、错误处理。
4. **安全**：注入风险、路径穿越、密钥泄露、对宿主数据的越权操作。
5. **测试**：测试是否真能复现问题、是否会因为改了断言而「假绿」。
6. **兼容**：是否破坏现有接口？是否需要版本号递增？

## 5. 标签（Tags）与发布

### 5.1 标签规范

```bash
git tag -a v1.2.0 -m "v1.2.0 —— <一句话变更摘要>"
git push origin v1.2.0
```

- 标签名必须是 `v<主>.<次>.<修订>`，与 `manifest.json` / `package.json` 的 `version` **完全一致**。
- 使用**附注标签**（`-a`），不要用轻量标签。
- **不在 `main` 上直接打标签**，从已合并的主干打。

### 5.2 发布检查清单

- [ ] 版本号已按 `../engineering/versioning.md` 规则递增
- [ ] `manifest.json` / `package.json` 的 `version` 已同步更新
- [ ] `CHANGELOG.md` 已写入本次版本的完整条目
- [ ] `README.md` 中若有版本相关内容已同步
- [ ] 全量测试通过
- [ ] 实机 / 浏览器验证通过
- [ ] 内置的 `src/client/vendor/ui-kit/` 副本版本与 CHANGELOG 记录一致
- [ ] 标签已创建并推送

## 6. 常见错误与纠正

| 错误 | 纠正 |
|---|---|
| 在主干分支直接提交并推送 | 切特性分支，走 PR |
| 提交信息写「更新代码」「修复问题」 | 用 `<类型>(<范围>): <具体主题>` |
| 一次提交混入 5 件事 | `git reset --soft HEAD~1` 后用 `git add -p` 拆分 |
| 混进 `node_modules/` 或 `.env` | 加入 `.gitignore`，`git rm --cached` 摘除后补提交 |
| 修改了 `src/client/vendor/ui-kit/` 下的文件 | 还原该目录改动，改走上游 issue 流程 |
| PR 描述写「已完成，没测」 | 补真实测试输出；确实没测就写明并说明如何验证 |
| 在他人 PR 上直接提交推送 | 推自己的分支，或在 PR 里提 review 建议 |
