# 版本号规范（语义化版本 SemVer）

> 统一采用 `1.0.0` 形式的语义化版本号，遵循 [SemVer 2.0.0](https://semver.org/lang/zh-CN/)。
> 与 `../AGENTS.md` §5.2、`./git-workflow.md` §5 配合使用。

---

## 1. 版本号格式

```
主版本号.次版本号.修订号
  1     .  0     .   0
```

**格式硬性要求：**

| 项 | 规则 |
|---|---|
| 形态 | `X.Y.Z`，三段，**不带前缀**（标签上才加 `v`） |
| 分隔符 | 半角点 `.` |
| 数值 | 非负整数，**不补零**（`1.0.0` 不是 `1.00.00`） |
| 预发布 | `X.Y.Z-alpha.1` / `-beta.2` / `-rc.1` |
| 构建号 | `X.Y.Z+20261021`（可选，不影响优先级） |

**正例**：`0.1.0`、`1.0.0`、`1.2.3`、`2.0.0-beta.1`、`1.0.0-rc.3`

**反例**：`v1.0`（少一段）、`1.0.0.1`（多一段）、`1.0.0.0`（多一段）、`01.0.0`（补零）、`latest`（不可比较）

## 2. 三个数字各自的含义与递增时机

### 2.1 主版本号（MAJOR，`X`）— 破坏性变更

**递增时机：出现下列任一情况时，主版本号 +1，次版本号与修订号归零。**

| 场景 | 说明 |
|---|---|
| **API 不兼容** | 删除了公开导出的函数/字段；修改了函数签名、参数顺序、参数含义 |
| **配置格式不兼容** | 设置项的键名变更、含义变更、默认值变更导致既有用户行为改变 |
| **数据结构不兼容** | 存储格式（localStorage / 文件 / 数据库）旧数据无法被新版直接读取，且**未提供迁移路径** |
| **宿主最低版本要求提高** | `minimum_client_version` / `engines` 提高，导致旧宿主无法运行 |
| **破坏性 DOM 契约变更** | 组件的 DOM 结构或 CSS 类名契约变更，导致下游样式失效 |
| **依赖破坏性升级** | 升级到上游的大版本且需要下游配合改动 |

**核心判断标准**：*旧版本的用户/集成方，升级后是否需要改代码才能继续正常工作？*
需要 → 主版本号 +1。

**必须做**：提供**迁移指引**（升级说明、旧数据迁移函数、CHANGELOG 中的 `BREAKING CHANGE` 段落）。

### 2.2 次版本号（MINOR，`Y`）— 向后兼容的新功能

**递增时机：新增了用户可见的能力，且不破坏任何现有用法。**

| 场景 | 说明 |
|---|---|
| 新增功能 | 新增面板、新增命令、新增设置项 |
| 新增可选配置 | 新增设置项，**默认值保持原有行为不变** |
| 新增 API | 新增导出函数/方法，不修改已有签名 |
| 新增能力开关 | 新增实验性功能的开关，默认关闭或默认安全 |
| 新增兼容支持 | 支持新的宿主版本或新的运行环境 |

**同时**：主版本号不变，修订号归零。

**注意**：新增功能的**默认行为不得改变既有用户看到的结果**。如果新功能默认开启且改变了既有行为 → 那是破坏性变更 → 主版本号 +1。

### 2.3 修订号（PATCH，`Z`）— 向后兼容的缺陷修复

**递增时机：修复缺陷，且不引入新功能、不改变任何已有接口。**

| 场景 | 说明 |
|---|---|
| 缺陷修复 | 逻辑错误、边界条件漏判、异常未捕获 |
| 崩溃修复 | 白屏、报错、无法打开面板 |
| 性能问题修复 | 内存泄漏、重复渲染、卡顿 |
| 显示问题修复 | 错位、样式异常、无障碍缺陷 |
| 文档修正 | 文档错误（仍按修订号发布，便于追踪） |
| 依赖补丁升级 | 升级到 `x.y.Z+1` 的补丁版本 |

**同时**：主版本号与次版本号都不变。

**注意**：如果修复过程中**顺手加了新功能** → 那是次版本号，不是修订号。保持单一职责。

### 2.4 速查表

| 改动内容 | 主 | 次 | 修订 | 示例 |
|---|:---:|:---:|:---:|---|
| 删除一个公开导出的函数 | +1 | 0 | 0 | `1.4.2` → `2.0.0` |
| 修改函数参数含义 | +1 | 0 | 0 | `1.4.2` → `2.0.0` |
| 设置项改名且无法自动迁移 | +1 | 0 | 0 | `1.4.2` → `2.0.0` |
| 提高宿主最低版本要求 | +1 | 0 | 0 | `1.4.2` → `2.0.0` |
| 新增一个面板 | 0 | +1 | 0 | `1.4.2` → `1.5.0` |
| 新增可选设置项 | 0 | +1 | 0 | `1.4.2` → `1.5.0` |
| 新增一个导出方法 | 0 | +1 | 0 | `1.4.2` → `1.5.0` |
| 修复空输入崩溃 | 0 | 0 | +1 | `1.4.2` → `1.4.3` |
| 修复样式错位 | 0 | 0 | +1 | `1.4.2` → `1.4.3` |
| 修复内存泄漏 | 0 | 0 | +1 | `1.4.2` → `1.4.3` |
| 升级补丁版依赖 | 0 | 0 | +1 | `1.4.2` → `1.4.3` |
| 修正文档错别字 | 0 | 0 | +1 | `1.4.2` → `1.4.3` |
| 纯重构，行为不变 | 0 | 0 | 0 | `1.4.2` → `1.4.2` |

> 纯重构（`refactor`）、纯格式化（`style`）、CI 配置调整（`ci`）**不触发版本递增**，但需要重新发布时可递增修订号。

## 3. 0.x 阶段的特殊规则

项目尚未发布稳定版（版本号 `0.x.y`）时，遵循以下约定：

- **`0.MINOR.PATCH`** 中，`MINOR` 承担「次版本」的语义，`PATCH` 承担「修订」的语义。
- **0.x 阶段允许在 MINOR 位引入破坏性变更**（这是 0.x 的惯例），但**必须在 CHANGELOG 中显式标注 `BREAKING CHANGE`**，并在 README 中标注「当前处于 0.x，不保证向后兼容」。
- **一旦发布 `1.0.0`，即进入严格 SemVer**，此后任何破坏性变更都必须递增主版本号，并提供迁移指引。
- 首个稳定版 `1.0.0` 的判定条件（全部满足）：
  - [ ] 核心功能闭环，用户可完整走通主流程
  - [ ] 公开 API / DOM 契约已稳定，不再预期结构性调整
  - [ ] 有完整的 CHANGELOG 与升级说明
  - [ ] 有可用的实机验证流程（自动化测试 + 手工验收清单）

## 4. 版本号的落地位置

**同一个版本号必须出现在以下所有位置，且完全一致：**

| 位置 | 字段 | 说明 |
|---|---|---|
| `package.json` | `version` | **唯一事实来源**，唯一需要手动修改的位置 |
| `manifest.json` | `version` | 宿主扩展管理器读取的版本，由守卫测试强制与 `package.json` 一致 |
| `src/server/Version.js` | — | 不硬编码版本，运行时从 `package.json` 读取 |
| Git 标签 | `vX.Y.Z` | 附注标签，发布时创建 |
| `CHANGELOG.md` | 标题 | `## [X.Y.Z] - YYYY-MM-DD` |

**一致性检查**（发布前必须跑通）：

```bash
# 两处版本号必须相等
node -e "const a=require('./package.json').version,b=require('./manifest.json').version;console.log(a===b?'OK '+a:'MISMATCH '+a+' vs '+b)"
```

不一致时**以 `package.json` 为准**（唯一事实来源），同步修正 `manifest.json`。

> **不要手工逐处改版本号。** `tests/version.test.js` 已内置守卫：校验 `package.json` /
> `manifest.json` / 服务端 `info.version` 三者一致，并校验前端具备「服务端 → manifest → 字面量」
> 三级版本来源。改完 `package.json` 后跑 `npm test`，不一致会被直接拦下。

> **内置的 `src/client/vendor/ui-kit/` 副本有独立版本**（当前 v2.5.0），与本项目版本**不要求一致**。两者在 CHANGELOG 中分别记录。

## 5. 提交类型与版本号的对应

提交信息类型（`./git-workflow.md` §2.2）与版本号递增的对应关系：

| 提交类型 | 触发的版本递增 |
|---|---|
| `feat` | 次版本号 +1（若同时有 `BREAKING CHANGE`，则主版本号 +1） |
| `fix` / `perf` | 修订号 +1 |
| `docs` / `style` / `refactor` / `test` / `build` / `ci` / `chore` | 不触发 |

**累积规则**：一个发布周期内累积了多个 `feat` → 发布时次版本号 +1；累积了多个 `fix` → 修订号 +1；两者都有 → **次版本号 +1**（修订号归零）。

> 即：**同一版本内不允许既有新功能又有破坏性变更**。有破坏性变更就一定是大版本。

## 6. 预发布版本

用于发布候选版本：

```
1.0.0-alpha.1    开发中，功能未完成，接口可能再变
1.0.0-alpha.2
1.0.0-beta.1     功能完整，进入验收
1.0.0-beta.2
1.0.0-rc.1       验收通过，等待发布
1.0.0-rc.2
1.0.0            正式发布
```

**规则：**

- 预发布版本**不用于生产分发**，仅供测试与验收。
- 预发布版本递增**只递增预发布号**（`alpha.1` → `alpha.2`），主次修订号不动。
- 从预发布转为正式版时，去掉预发布后缀，版本号与 `rc` 阶段的主次修订号**完全相同**。
- 正式版发布后**不得**再回到预发布版本号。

## 7. CHANGELOG 维护

### 7.1 格式

遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)，按版本倒序：

```markdown
# 变更日志

本文件记录项目的所有重要变更。

格式基于 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)，
版本号遵循 [语义化版本](https://semver.org/lang/zh-CN/)。

## [未发布]

### 新增
- 计划中的功能

## [1.2.0] - 2026-10-21

### 新增
- 条目列表支持批量标签操作 [#58](https://github.com/zgy-beep/ST-WebDAV/issues/58)
- 新增批量操作确认弹窗

### 修复
- 修复空输入导致的解析崩溃 [#42](https://github.com/zgy-beep/ST-WebDAV/issues/42)
- 修复面板滚动跳动问题

### 变更
- 运行时设置接口改为异步（**BREAKING CHANGE**：所有调用方需 await）

## [1.1.0] - 2026-09-30

### 新增
- 初始稳定功能集
```

### 7.2 分类

固定使用以下小节标题（无内容则整节省略）：

| 小节 | 含义 | 对应提交类型 |
|---|---|---|
| `### 新增` | 新功能 | `feat` |
| `### 修复` | 缺陷修复 | `fix` |
| `### 变更` | 行为变更（含破坏性） | `feat!` / `refactor` |
| `### 弃用` | 即将移除的功能 | — |
| `### 移除` | 已移除的功能 | — |
| `### 修复` | — | — |
| `### 安全` | 安全相关修复 | `fix` |
| `### 内部` | 不影响使用者的内部变更 | `chore` / `refactor` / `ci` / `test` / `build` / `style` / `docs` |

### 7.3 规则

- **每个发布的版本必须有 CHANGELOG 条目**，没有例外。
- 条目描述**面向使用者**：说「用户能做什么」，不说「重构了哪个类」。
- 破坏性变更必须在 `### 变更` 下用 **BREAKING CHANGE** 开头，并给出迁移方式。
- 有 issue 编号的条目附链接。
- **`## [未发布]` 段落常驻**，累积未发布的改动。

## 8. 发布流程

```
① 确认改动分类
   └─ 用 §2.4 速查表判断该递增哪一位
       ↓
② 更新版本号
   └─ package.json + manifest.json 同步更新
       ↓
③ 更新 CHANGELOG
   └─ 把 [未发布] 段落归入新版本，写清日期
       ↓
④ 全量验证
   └─ 测试 + 检查 + 实机验证
       ↓
⑤ 提交
   └─ chore(release): 发布 vX.Y.Z
       ↓
⑥ 打标签并推送
   └─ git tag -a vX.Y.Z -m "vX.Y.Z —— <摘要>"
   └─ git push origin vX.Y.Z
       ↓
⑦ 发布到分发渠道
   └─ 推送 Git 标签，同步分发包
```

## 9. 常见错误

| 错误 | 正确做法 |
|---|---|
| 修 bug 也升主版本 | 修 bug → 修订号 +1 |
| 加功能只升修订号 | 加功能 → 次版本号 +1 |
| 破坏性变更写成 `fix` | 用 `feat!:` 或 `refactor!:` 并写 `BREAKING CHANGE` |
| 版本号只改了 `package.json` | `manifest.json` 必须同步 |
| 标签名与版本号不一致 | 标签必须是 `v` + 版本号 |
| 同一版本既有新功能又有破坏性变更 | 拆成两次发布 |
| 预发布版本号用于生产 | 预发布仅供验收 |
| CHANGELOG 写「优化了代码」 | 写用户视角的变化 + issue 链接 |
