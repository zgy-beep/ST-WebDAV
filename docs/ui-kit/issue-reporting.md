# 向上游 ui-kit 提交 Issue 的规范

> 适用场景：本项目依赖 `zgy-beep/ui-kit`（UI 组件库）时，发现该组件库存在**功能缺陷**或**能力缺失**。
> 关联规则见 `../AGENTS.md` §6。
>
> **核心原则：不在本地改写 ui-kit，改为向上游提交 issue。**
> 本地改写会制造分叉，缺陷会扩散到其它共用该库的插件，且上游修复后本地补丁必然冲突。

---

## 1. 什么时候必须提 issue

| 情况 | 动作 |
|---|---|
| ui-kit 组件行为不符合预期（有明确 bug） | 提 **bug issue** |
| ui-kit 缺少我们需要的能力 | 提 **feature request issue** |
| ui-kit 文档与实际行为不一致 | 提 **bug issue**，标注「文档错误」 |
| ui-kit 无障碍/性能/兼容性存在缺陷 | 提 **bug issue** |
| 只是我们想要一个和 ui-kit 风格不同的定制效果 | **不提 issue**，业务侧自建样式 |

**判断口径**：*这个问题的根源在 ui-kit 还是在我们的用法？*
- 根源在 ui-kit（组件自身逻辑错、API 缺失、文档说错）→ 提 issue。
- 根源在用法（我们没按文档用、我们传错了参数）→ 修我们的代码，**不提 issue**。

> 提 issue 前先读上游 `zgy-beep/ui-kit` 的 README 对应章节，确认不是误用。

## 2. Issue 标题格式

```
[组件名] 类型: 一句话描述问题
```

**规则：**

| 项 | 要求 |
|---|---|
| `[组件名]` | 必填。取 ui-kit 中的实际组件/模块名（`Button`、`Panel`、`Tabs`、`Toast`、`nvui-api`、`components.css` 等），**必须与上游命名一致** |
| 类型 | `bug` / `feature` / `docs` |
| 冒号 | 半角 `: `（冒号 + 一个空格） |
| 描述 | 一句话说清问题，**不含句号结尾**，≤ 60 字符 |

**正例：**

```
[Button] bug: 禁用态下点击仍会触发 onClick
[Panel] feature: 缺少对宿主模态层动态开关的响应
[Toast] bug: 快速连续调用时后一条提示覆盖前一条
[components.css] docs: §7.14 示例与实际 DOM 结构不一致
[nvui-api] bug: createPanel 传入相同 id 时未做去重
```

**反例：**

```
按钮有问题                     ← 无组件名、无类型、不说现象
fix button                    ← 英文、无类型
[Button] 按钮的点击事件在禁用的时候还是会触发，麻烦修一下。  ← 带句号、过长
[button] bug: ...             ← 组件名大小写与上游不一致
```

## 3. Issue 正文必备要素

**以下 7 项全部为必填**，缺一项不予提交：

### 3.1 环境信息

```
- ui-kit 版本：v2.8.0
- 宿主环境：SillyTavern 1.19.0（浏览器：Chrome 131）
- 主题：深色 / 浅色
- 本项目集成方式：整目录复制内置
```

### 3.2 问题描述（一句话）

用一句话说明**现象**，不含推测原因。

```
禁用态按钮在鼠标点击时依然会触发 onClick 回调。
```

### 3.3 复现步骤（编号、可执行）

**必须是最小可复现路径**，每步一个动作：

```
1. 打开任意面板，定位到工具栏区域
2. 找到「删除」按钮并设置 disabled = true
3. 用鼠标点击该按钮
4. 观察：回调被触发，控制台出现删除请求
```

要求：
- 步骤里不出现「我」「你」，用祈使句。
- 不省略关键动作（「然后就出问题了」不算步骤）。
- 能复现的路径要写明**具体入口**（哪个面板、哪个设置页）。

### 3.4 期望行为（Expected）

```
disabled 为 true 时，点击不应触发 onClick，也不应发出任何请求。
```

### 3.5 实际行为（Actual）

```
disabled 为 true 时点击，onClick 仍被触发，删除请求已发出。
```

### 3.6 影响范围与严重度

```
影响范围：所有使用 nvui-btn 且设置 disabled 的场景
严重度：P1（功能错误，可能造成数据误删）
```

严重度口径：

| 级别 | 判定 |
|---|---|
| **P0** | 安全漏洞、数据丢失/损坏、宿主整体不可用 |
| **P1** | 核心功能错误、明显交互失效、无障碍红线 |
| **P2** | 次要功能异常、视觉明显偏差、性能可感知下降 |
| **P3** | 体验瑕疵、文案/文档问题 |

### 3.7 复现代码或证据

给出**最小可运行片段**，或实机观测数据。

```js
// 最小复现代码
const btn = NVUI.createButton({ label: '删除', disabled: true, onClick: () => console.log('触发') });
btn.addEventListener('click', () => console.log('监听器也被触发'));
```

或实测数据：

```
实机观测：disabled=true 时，click 事件的 target 仍为按钮元素，
isTrusted=true，未被浏览器拦截。
```

## 4. Issue 正文完整模板

```markdown
## 组件 / 模块

`nvui-btn`（Button）

## 问题描述

禁用态按钮在鼠标点击时依然会触发 onClick 回调。

## 环境

- ui-kit 版本：v2.8.0
- 宿主：SillyTavern 1.19.0
- 浏览器：Chrome 131
- 主题：深色
- 集成方式：整目录复制内置

## 复现步骤

1. 打开任意面板，定位到工具栏区域
2. 找到「删除」按钮并设置 `disabled = true`
3. 用鼠标点击该按钮
4. 观察：回调被触发，控制台出现删除请求

## 期望行为

`disabled` 为 `true` 时，点击不应触发 `onClick`，也不应发出任何请求。

## 实际行为

`disabled` 为 `true` 时点击，`onClick` 仍被触发，删除请求已发出。

## 影响范围

所有使用 `.nvui-btn` 且设置 `disabled` 的场景。

严重度：**P1**（功能错误，可能造成数据误删）

## 复现代码

```js
const btn = NVUI.createButton({ label: '删除', disabled: true, onClick: () => console.log('触发') });
```

## 补充说明

该行为在 v2.4.0 是否已存在？若已存在，是否属于设计意图？
我们可以在上游修复前先做业务侧隔离，但不修改 ui-kit 源码。
```

## 5. Feature Request 的差异

需求类 issue 在上述要素基础上，**替换**「期望行为/实际行为」为：

### 5.1 需求背景

说明**为什么需要**这项能力，以及现有方案为何不够用：

```
当前多个宿主面板需要响应宿主的模态层开关，但组件没有暴露相应能力，
目前只能在业务侧用 MutationObserver 手动同步，成本高且易出错。
```

### 5.2 期望的 API 形态

尽量给出具体建议（哪怕是草案），降低上游决策成本：

```js
// 期望：createPanel 增加宿主模态响应选项
const panel = NVUI.createPanel({
  title: '示例',
  hostModalAware: true,   // 建议：宿主模态时自动降级
});
```

### 5.3 备选方案

说明你考虑过但不适用的方式，以及为什么不选：

```
备选一：在业务侧监听 dialog[open] 事件 —— 宿主未来更换模态实现即失效。
备选二：直接用 z-index 硬压 —— 宿主 inert 机制下无效。
```

**标题示例：**

```
[Panel] feature: 增加宿主模态层响应的显式开关
```

## 6. 提交前的自查清单

- [ ] 已读过上游 `zgy-beep/ui-kit` 的 README 对应章节，确认不是误用
- [ ] 已搜索过上游已有 issue，确认不是重复
- [ ] 标题符合 `[组件名] 类型: 描述` 格式，组件名与上游一致
- [ ] 正文包含全部 7 项必备要素（环境 / 描述 / 步骤 / 期望 / 实际 / 影响范围 / 证据）
- [ ] 复现步骤是最小路径，每步一个动作，无「然后就坏了」式描述
- [ ] 期望行为与实际行为**成对出现**
- [ ] 严重度已按 P0~P3 口径评定
- [ ] 附了最小复现代码或实机观测数据
- [ ] **没有**在本地修改 ui-kit 源码来"验证"这个 issue
- [ ] 已在项目内登记（见 §7）

## 7. 项目内的登记与跟踪

提 issue 后，**必须**在本项目留痕，便于后续跟进与升级：

### 7.1 登记位置

在项目内维护一份上游问题追踪表（建议 `docs/ui-kit/known-issues.md`）：

| 编号 | 组件 | 问题摘要 | 严重度 | 状态 | 上游链接 | 首次登记 |
|---|---|---|---|---|---|---|
| 1 | nvui-btn | 禁用态点击仍触发 onClick | P1 | 待修复 | [#12](https://github.com/zgy-beep/ui-kit/issues/12) | 2026-10-21 |
| 2 | Panel | 缺少宿主模态响应能力 | P2 | 待上游确认 | [#15](https://github.com/zgy-beep/ui-kit/issues/15) | 2026-10-21 |

**状态取值**：`待上游确认` / `已确认-待修复` / `已修复待同步` / `已同步` / `已确认-不修`

### 7.2 代码中的引用

若业务侧写了临时隔离层，**必须在代码注释中引用上游编号**：

```js
// 临时绕过：ui-kit#12 —— 禁用态按钮点击仍触发 onClick
// 移除条件：ui-kit 修复并升级到 >= v2.6.0 后删除本文件
```

### 7.3 跟进流程

```
发现疑似缺陷
    ↓
读 ui-kit README 对应章节，排除误用
    ↓
搜上游已有 issue，排除重复
    ↓
按 §4 模板写 issue → 自查 §6 清单 → 提交
    ↓
把 issue 编号登记到 docs/ui-kit/known-issues.md
    ↓
（如需先解阻塞）写隔离层，注释引用编号 + 移除条件
    ↓
上游修复 → 升级内置 ui-kit 副本 → 跑全量测试 → 删除隔离层 → 状态改为「已同步」
```

> **重要**：状态改为「已确认-不修」时，**必须附实测数据与复现脚本**，不允许仅凭推理下结论。

## 8. 绝不做的事

| ❌ 禁止 | 原因 |
|---|---|
| 在本地 `src/client/vendor/ui-kit/` 里改源码「先试试」 | 制造分叉，上游修复后必然冲突 |
| fork 一份 ui-kit 改完再合回自己项目 | 同上，且违反上游分发约定 |
| 用 `!important` / 内联样式 / 覆写类名打补丁 | 绕过契约，升级即失效，且可能污染其它插件 |
| 把 issue 提给自己项目当作记录 | 上游问题要在上游仓库提，才能被真正修复 |
| issue 只写「有个 bug」 | 无法定位，无法复现，上游无法处理 |
| 凭推测断言「这是设计意图」 | 实测拿数据再下结论 |
| 未测就写「已确认-不修」 | 必须附实测数据与复现脚本 |
