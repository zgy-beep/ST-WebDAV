# ADR-001：加密备份采用密文格式 v02

- 状态：已接受
- 日期：2026-10-26
- 相关：无上游 issue；依据 CODE_REVIEW.md 的 L1/L2 与 src/server/CryptoHelper.js

## 背景

ST-WebDAV 提供可选的端到端加密（AES-256-GCM）。v01 密文头部为
`[8B MAGIC 'STWBDV01'][16B SALT][12B IV][密文][16B GCM TAG]`，KDF 固定为
PBKDF2-HMAC-SHA256 100,000 次（`src/server/CryptoHelper.js:11`、`:27`）。

本轮审查确认两个问题：

- L1：100k 次低于 OWASP 对 PBKDF2-HMAC-SHA256 的建议基线（`CODE_REVIEW.md:117`）；
- v01 头部不携带 KDF 参数，任何强度调整都要再改一次格式。

若把迭代次数写进头部以换取升级自由度，又会引入 L2：恶意密文可声明超大迭代数
做 CPU 消耗型 DoS（`CODE_REVIEW.md:118`）。

## 决策

1. 写出的密文一律为 v02 格式：
   `[8B 'STWBDV02'][4B uint32BE 迭代次数][16B SALT][12B IV][密文][16B GCM TAG]`
   （`src/server/CryptoHelper.js:8-11`、`:91-97`）。
2. KDF 使用 PBKDF2-HMAC-SHA256，默认迭代 210,000 次，密钥派生走异步
   `deriveKeyAsync()`，不阻塞事件循环（`CryptoHelper.js:29`、`:62-64`、`:116`）。
3. 解密时读取头部声明的迭代次数，并 clamp 到 `[100000, 1000000]`；越界直接拒绝
   （`CryptoHelper.js:38-39`、`:194-197`）。
4. v01 只读向后兼容：识别 `STWBDV01` 魔数并按 100,000 次派生，历史备份仍可还原
   （`CryptoHelper.js:201-208`；回归测试 `tests/share.test.js:219-240`）。
5. 新备份一律写 v02，不再写 v01；v01 仅保留在读取路径。

## 备选方案

- **保持 v01**：改动最小，但 KDF 强度无法提升，且以后每次调参都要再改格式，与
  「安全降级视为破坏性变更」（AGENTS.md §2.1）的方向冲突；已否决。
- **换用 argon2**：抗 GPU 更好，但需新增原生依赖，违背当前「运行时依赖仅 3 个」的
  约束（AGENTS.md §7），且目标环境常见低配 NAS；已否决。
- **默认迭代直接拉到 1,000,000**：备份/还原耗时随之上升，clamp 上界是按实测 CPU 成本
  定的（`CryptoHelper.js:35-36`）；默认取 210k，保留头部字段供未来平滑上调。

## 后果

- 正面：KDF 强度提升；头部携带迭代次数，后续调参无需再改格式；异步派生不阻塞事件
  循环；v01 历史备份可继续还原；clamp 阻断迭代次数拉高型 CPU DoS。
- 负面：密文头增加 4 字节；迭代数提升 2.1 倍，单次加解密耗时同比增加（按迭代数推算，
  非实测）；旧版本插件无法解密 v02 备份，升级后不可无痛回退旧版。
- 负面：解密流在 GCM Auth Tag 校验通过前就会 push 明文（`CryptoHelper.js:153-156`
  有明确的安全红线注释），安全性依赖「全量收集后再解压」的调用方式。
- 需要配套做的事：
  - 保持调用方「先收齐明文、验证 Auth Tag、再解压写盘」的链路；不得改为边解密边写盘，
    除非先完成 tag 校验；
  - clamp 边界（<100000 / >1000000）目前没有专门测试，是否补测待确认；
  - 任何弱化 210k 默认值、clamp 区间或 v01 兼容的改动，都必须先以新 ADR 修订本决策；
  - 在 CHANGELOG/README 说明「新备份为 v02、旧 v01 备份仍可还原」，由对应文档任务负责。
